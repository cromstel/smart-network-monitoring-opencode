# Performance

Generated by `npm run perf`. Do not edit by hand — rerun the harness.

Targets come from `PRD.md` §5. Each row is a real measurement against a real
database at the dataset size described below; the run fails if any p95 misses its
target, so this table cannot drift away from reality without CI noticing.

## What each measurement does

- **30-day history query** — `listForDeviceBetween` for one device across 30 days; returns 2,880 raw rows.
- **Scan cycle, DB side (simulated backend)** — A complete `scanOnce` against the simulated backend, which yields 12 devices: upserts, connection logs, offline detection, alert evaluation and the scan-history row. This is everything the application does per cycle **except** the network probe itself.
- **Network probe (simulated backend)** — The probe call alone, which for the simulated backend is a static array. It bounds nothing meaningful and is included only to show the probe is not where the time goes. **The real /24 probe is not measured here** — see "Known limits".
- **Device list (100 devices)** — One page of the device table, the query behind the dashboard on load.
- **Stats fan-out (100 devices)** — Latest-sample lookup for every device in one query. This is the join the dashboard runs on every render and on every SSE-triggered refetch.

## Method

- Warmup iterations are discarded so the numbers are steady state, not JIT warm-up.
  The count is in the `n` column as `timed+warmup`.
- The **p95** is compared against the target, because a median hides the tail that a
  user actually feels. Cheap reads take 20 samples; anything that writes to the
  database takes fewer, since repeating it would distort the very numbers being
  measured.
- Dataset figures are deterministic (`Math.random` is not used), so a regression is
  attributable to the code rather than to a differently-shaped dataset.

## Known limits of this harness

- **The real /24 probe is not measured.** The `Scan cycle, DB side` row times
  everything the application does per cycle, but the ARP sweep itself needs
  `CAP_NET_RAW` and a live /24 to talk to, neither of which exists on the machine
  this ran on. The PRD §5 "under 30s for a /24" target is therefore **partially**
  evidenced: the application-side budget is measured, the network-side budget is not.
  `arp-scan --localnet` against a real subnet is the missing measurement.
- **First contentful paint is not measured here.** It needs a browser and a running
  server, so it belongs to the Playwright suite. The PRD §5 target of "under 2s on a
  warm cache" is not evidenced by this file.
- Numbers are from a single machine. Absolute values differ elsewhere; the
  pass/fail gate is what carries across environments, not the milliseconds.
- MySQL numbers come from running this harness with `DB_CLIENT=mysql` against the
  Compose stack. The table records whichever dialect was used.

## Observations

The slowest operation is **Stats fan-out (100 devices)** at 172.8ms p95. It is inside its target, but it is the query behind every dashboard render and every SSE-triggered refetch, so it is the one to watch if the UI ever feels slow. It is a correlated subquery joined back over the whole metrics table; an index on `(device_id, timestamp)` is what keeps it from being far worse.

The scan-cycle and probe rows run against the same database, so their values move a few
